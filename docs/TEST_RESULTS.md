# Результаты тестирования ядра (`:core`)

Прогнано автоматически, офлайн, прямо в песочнице разработки — без Android SDK
(он для `:core` не нужен, см. `ARCHITECTURE.md` §1). Инструменты: `kotlinc`
1.3.31 и `junit4` 4.13.2 из штатного репозитория Ubuntu (пакеты `kotlin` и
`junit4`), без доступа к Maven/Google (он для этой сборки не требовался).

## Как повторить

```bash
JUNIT_CP="/usr/share/java/junit4.jar:/usr/share/java/hamcrest-core.jar"
kotlinc android-project/core/src/main/kotlin/com/astrostacker/core/*.kt \
        android-project/core/src/test/kotlin/com/astrostacker/core/*.kt \
        -cp "$JUNIT_CP" -include-runtime -d build/core-tests.jar

java -cp "build/core-tests.jar:$JUNIT_CP" org.junit.runner.JUnitCore \
  com.astrostacker.core.GeometryTest \
  com.astrostacker.core.EarthRotationModelTest \
  com.astrostacker.core.StarDetectorTest \
  com.astrostacker.core.RegistrationTest \
  com.astrostacker.core.StackCombinerTest \
  com.astrostacker.core.MidtoneStretchTest \
  com.astrostacker.core.BackgroundExtractorTest \
  com.astrostacker.core.DarkFrameCalibratorTest \
  com.astrostacker.core.ColorSpaceTest \
  com.astrostacker.core.PipelineIntegrationTest
```

После того как проект открыт в Android Studio (или в CI с доступом к Google
Maven), те же файлы автоматически становятся обычными Gradle-тестами:
`./gradlew :core:test` — источники не переписываются, конфигурация
`core/build.gradle.kts` уже ссылается на `src/test/kotlin`.

`Pipeline.kt` также был рефакторен уже после первого прогона (см. ниже "реальные
ошибки"): фон/нейтрализация/растяжка/шумоподавление вынесены из `run()` в
отдельную публичную `postProcess()`, чтобы `:app` мог дёшево пересчитывать
только эту часть (ползунок растяжки, переключатель шумоподавления) без
повторной детекции звёзд и стекинга — без изменения самой логики. Это
поведение-сохраняющий рефакторинг (просто перенос кода в функцию), но после
него весь набор тестов был прогнан заново теми же 36 тестами — совпадение
результата подтверждено, а не предполагается.

## Реальные ошибки, найденные и исправленные в процессе (а не просто опечатки)

Тестирование не было формальностью — на первом прогоне 2 теста из 29 упали и
вскрыли настоящие логические ошибки, которые не были бы заметны на глаз:

1. **Апостериорная проверка поворота была не строгой.** Изначальное условие
   срабатывания предупреждения включало отсечку «не проверять, если ожидаемый
   угол меньше 0.01°» — что как раз ГЛУШИЛО предупреждение именно в самом
   показательном случае несоответствия (когда интервал между кадрами короткий,
   ожидаемый поворот почти нулевой, а найденный — большой, то есть что-то
   явно пошло не так). Исправлено: осталась только пропорциональная +
   абсолютная (0.05°, на обычное дрожание камеры) допустимая погрешность,
   без отсечки по абсолютной величине ожидаемого угла. См. `FrameRegistrator.kt`.
2. **Автоподбор растяжки мог "сжечь" изображение в белый.** После вычитания
   градиента фон близок к нулю (это и есть цель вычитания), а формула
   `autoMidtoneForBackground` при входном фоне около нуля требует `m→0`, что
   растягивает шум фона так же агрессивно, как сигнал звёзд — итоговое
   изображение оказывается почти сплошь белым, и на нём буквально не находится
   ни одной звезды (это и поймал `PipelineIntegrationTest`: 0 из 35 звёзд).
   Исправлено на двух уровнях: (а) `Pipeline.kt` теперь оценивает фон для
   растяжки как `max(медиана, 2×σ шума фона)` — ниже собственного шумового
   пола фон статистически неотличим от нуля, тянуть растяжку к этому уровню
   бессмысленно; (б) `MidtoneStretch.autoMidtoneForBackground` дополнительно
   ограничивает результат диапазоном `[0.02, 0.98]` как защиту на уровне самой
   функции, независимо от того, что ей передали.

Третья ошибка нашлась позже не на синтетике, а на настоящих присланных фото
(см. `TESTING_PLAN.md`) — синтетический фон в `BackgroundExtractorTest` был
чистым градиентом без резких тёмных областей и потому её не ловил:

3. **Тёмный силуэт переднего плана (горы) портил подгонку фона даже вдали от
   себя.** Полином фона (`BackgroundExtractor.kt`) не отличал "тёмный силуэт
   горы" от "легитимно тёмный угол из-за виньетирования" и тянул всю гладкую
   поверхность вниз. На реальном стеке это проявилось как нефизичный тёмный
   "купол" на небе и цветные пятна на самом силуэте горы. Исправлено
   итеративным робастным отсевом ячеек, которые намного темнее уже
   подогнанной модели в своей же точке (`Config.darkOutlierSigmaMultiplier`);
   регрессия закреплена новым тестом (см. таблицу выше). Границы этого
   исправления (не спасает при доле переднего плана ≥20% высоты кадра) - в
   комментариях к самому `Config.darkOutlierSigmaMultiplier`.

## Что НЕ проверено этими тестами (честно, по границе применимости)

- Реальные фотографии со смартфона (шум сенсора, паттерн Байера/демозаик,
  атмосферная рефракция, блики, засветка от домов/фонарей, движущиеся объекты
  переднего плана) — синтетика упрощает многое из этого. Настоящая проверка —
  на присланных 15-20 фото, см. `TESTING_PLAN.md`.
- Android-специфичный код `:app` (декодирование Bitmap/HEIC/DNG, работа с
  памятью на реальном телефоне, Compose-экраны) — не скомпилирован в этой
  среде (нет доступа к Android SDK/Google Maven, см. `ARCHITECTURE.md` §1),
  поэтому не может быть протестирован здесь в принципе. Единственное
  исключение — `ColorSpace.kt` (sRGB↔линейное для конвертации `Bitmap` в
  `FloatImage` и обратно): сама формула не зависит от Android API, поэтому
  вынесена в `:core` и протестирована по-настоящему (см. таблицу выше); а вот
  её реальное использование при декодировании настоящего `Bitmap` в `:app` —
  нет.
- Экстремально широкий угол/дисторсия объектива (влияет на точность
  приближения "подобием", см. `ARCHITECTURE.md` §3) — не смоделировано в
  синтетическом небе (там идеальная точечная проекция без дисторсии).
