# Литература и первоисточники

Документ собран для проекта AstroStacker — Android-приложения для склейки (стекинга)
астрофотографий. По каждому этапу конвейера обработки указан первоисточник, что именно
из него используется и как это отражено в коде `:core`. Все ссылки проверены (сентябрь 2026).

## 0. Методология

В любительской астрофотографии есть де-факто стандартный конвейер: детекция звёзд →
геометрическая регистрация кадров → отбраковка выбросов и комбинирование (стекинг) →
удаление градиента фона → нелинейная растяжка → шумоподавление/цветокоррекция.
Ниже — научные первоисточники этого конвейера и то, как его реализуют существующие
инструменты (DeepSkyStacker, Starry Landscape Stacker, Astroalign, PixInsight, Siril),
на поведение которых имеет смысл ориентироваться при тестировании.

### 0.1 Линейный свет и гамма-кодирование (sRGB): методологическая тонкость, общая для всех этапов

Отдельно стоит проговорить момент, который легко упустить в любительских руководствах,
но который влияет на корректность каждого этапа из перечисленных выше и ниже: JPEG/HEIC
с телефона хранит не физическую яркость света, а результат гамма-кодирования (sRGB OETF) —
стандарт **IEC 61966-2-1:1999 "Multimedia systems and equipment — Colour measurement and
management — Part 2-1: Default RGB colour space — sRGB"**
(https://webstore.iec.ch/en/publication/6169; общедоступное изложение той же формулы —
https://en.wikipedia.org/wiki/SRGB, раздел о передаточной функции). Обратное
преобразование (декодирование gamma → linear) — кусочно-линейное вблизи нуля и степенное
дальше:

```
linear = c / 12.92,                     c ≤ 0.04045
linear = ((c + 0.055) / 1.055)^2.4,     c > 0.04045
```

Усреднение при стекинге (раздел 3), вычитание фонового градиента (раздел 4) и формула MTF
(раздел 5) статистически и физически корректны только над величинами, пропорциональными
реальному потоку фотонов, — то есть над линейными значениями, а не над гамма-кодированными
байтами. Усреднить «в лоб» два gamma-encoded пикселя — не то же самое, что усреднить
реальную яркость и закодировать результат: из-за выпуклости гамма-кривой это даёт
систематическое, а не случайное отклонение, которое накопится за весь конвейер. Поэтому
декодирование sRGB→linear выполняется сразу при загрузке кадра, до детекции звёзд и
регистрации, весь конвейер (разделы 1–6) считает в линейном пространстве, и только
самый последний шаг — подготовка PNG для сохранения в галерею — кодирует результат
обратно linear→sRGB. Реализовано в `ColorSpace.kt` (таблица на 256 узлов для быстрого
декодирования 8-битного канала при загрузке, точная формула — для кодирования обратно при
сохранении); это единственный модуль `:core`, который не привязан к одному конкретному
этапу конвейера, а «оборачивает» все остальные этапы с обоих концов.

## 1. Обнаружение звёзд (детекция источников)

- **Bertin, E., Arnouts, S. (1996). "SExtractor: Software for source extraction."
  Astronomy & Astrophysics Supplement Series, 117, 393–404.**
  DOI: 10.1051/aas:1996164. https://aas.aanda.org/articles/aas/pdf/1996/08/ds1060.pdf
  Классическая работа по автоматическому обнаружению источников на астрономических
  изображениях: фон оценивается локально (сеткой ячеек с σ-клиппингом), источник —
  связная область пикселей выше порога `фон + k·σ`, для каждого источника считаются
  форма/поток/центроид. Наш детектор звёзд в `StarDetector.kt` использует ту же схему:
  локальный фон по сетке → порог по σ → связные компоненты → фильтр по площади/округлости
  → интенсивностно-взвешенный центроид.
- **Практическая реализация (DeepSkyStacker):** звезда определяется как «округлый объект,
  яркость которого равномерно спадает во всех направлениях», центр уточняется подгонкой
  гауссианы по профилю яркости; порог по умолчанию — 10% от максимальной яркости кадра.
  http://deepskystacker.free.fr/english/technical.htm — использовано как сверочный
  ориентир поведения (сколько звёзд типично нужно, как ведёт себя порог).

## 2. Геометрическая регистрация кадров (в т.ч. вращение неба)

### 2.1 Почему кадры вообще нужно поворачивать, а не только сдвигать

Земля вращается с угловой скоростью, задаваемой звёздными (сидерическими) сутками:
T = 86164.0905 с = 23ч56м4.0905с (https://en.wikipedia.org/wiki/Sidereal_time).
Отсюда скорость видимого вращения звёздного неба:

```
ω = 360° / 86164.0905 с = 1 296 000″ / 86164.0905 с ≈ 15.041 ″/с
```

(эквивалентно ω ≈ 7.2921159×10⁻⁵ рад/с — стандартная константа скорости вращения Земли).
Для неподвижной на штативе камеры это означает: между кадрами, снятыми последовательно,
звёздное поле не просто «сдвигается» — оно поворачивается вокруг точки полюса мира,
спроецированной на кадр (эта точка может быть далеко за пределами кадра — тогда поворот
на глаз похож на чистый сдвиг, но геометрически это всё равно поворот). Поэтому
регистрация «только по сдвигу» (как в дневной фотографии) для астрофото in principle
неверна и на широком поле или длинной серии даёт видимое «расползание» звёзд при стекинге.
Отсюда требование пользователя «считывать вращение планеты» — реализовано как
`EarthRotationModel.kt`: по EXIF-меткам времени двух кадров считается ожидаемый угол
поворота ω·Δt, который используется (а) как диагностика/лог для пользователя и
(б) апостериорная проверка результата регистрации (если найденный поворот сильно
расходится с ожидаемым — вероятно, кадр испорчен: облако, самолёт, шевеление камеры).
Он НЕ участвует как вход в сам алгоритм подгонки преобразования — см. ниже почему.

### 2.2 Почему поворот всё равно ищут эмпирически, по звёздам, а не только физической моделью

Формула выше даёт лишь модуль ожидаемого поворота. Она не знает: (а) где именно на
матрице проецируется полюс мира (нужны точные азимут/высота камеры), (б) не сдвинулся
ли слегка сам штатив/телефон между кадрами, (в) дисторсию объектива. Поэтому все
известные инструменты (DeepSkyStacker, Starry Landscape Stacker, Sequator, Astroalign)
находят полное геометрическое преобразование (поворот+сдвиг+масштаб) эмпирически,
сопоставляя сами звёзды между кадрами, а не вычисляя его из астрономии/геолокации.
Наш `FrameRegistrator.kt` делает так же; физическая модель используется только как
апостериорная проверка правдоподобия результата.

Более того, строго говоря, преобразование «поворот+сдвиг+масштаб» (подобие) —
лишь приближение. Точный результат поворота 3D-сцены вокруг оси, проходящей через
оптический центр камеры, — проективная гомография `H = K·R·K⁻¹` (стандартный факт
проективной геометрии камеры, см., например, Hartley, R., Zisserman, A. "Multiple
View Geometry in Computer Vision", 2nd ed., Cambridge University Press, 2004,
глава 8). Гомография вырождается в чистый 2D-поворот, только если ось вращения
совпадает с оптической осью камеры; для полюса мира это, как правило, не так.
На практике при небольшом угле поворота (доли градуса — единицы градусов, то есть
при интервалах между кадрами от секунд до пары минут) и не сверхширокоугольном
объективе приближение подобием работает достаточно хорошо — этим и объясняется,
почему все перечисленные инструменты используют именно его. На сверхширокий угол
(например, ультраширокий модуль S24 Ultra) погрешность этого приближения у краёв
кадра может стать заметной — на этот случай в `FrameRegistrator.kt` есть эскалация
до аффинного преобразования (6 степеней свободы), см. `ARCHITECTURE.md`, §3.

- **Groth, E. J. (1986). "A pattern-matching algorithm for two-dimensional coordinate
  lists." The Astronomical Journal, 91, 1244–1248.**
  Исторический первоисточник идеи: для каждой звезды и её ближайших соседей строятся
  треугольники; отношения длин сторон треугольника инвариантны к повороту, сдвигу и
  (частично) масштабу — по ним ищутся соответствия звёзд между кадрами без знания
  исходного преобразования.
- **Beroiz, M., Cabral, J. B., Sanchez, B. (2020). "Astroalign: A Python module for
  astronomical image registration." Astronomy and Computing, 32, 100384.**
  DOI: 10.1016/j.ascom.2020.100384. Код: https://github.com/quatrope/astroalign
  Современная, чистая реализация идеи Гроута: для каждой звезды берутся 4 ближайших
  соседа, строятся все `C(5,3)=10` треугольников, инвариант — нормализованные
  отношения сторон; инварианты обеих картинок ищутся через k-d дерево; преобразование
  принимается, если объясняет ≥80% (или ≥10, что меньше) точек. Наш
  `TriangleMatcher.kt` реализует ту же схему (независимая реализация по описанию
  алгоритма и общей идее Groth 1986 — без копирования кода Astroalign, лицензия
  которого — BSD-3, но код не заимствуется, чтобы не тащить чужую кодовую базу в проект).
- **Fischler, M. A., Bolles, R. C. (1981). "Random Sample Consensus: A Paradigm for
  Model Fitting with Applications to Image Analysis and Automated Cartography."
  Communications of the ACM, 24(6), 381–395.** DOI: 10.1145/358669.358692
  Классический RANSAC — используется в `RansacTransformFitter.kt` для отбраковки
  ложных сопоставлений звёзд перед финальной подгонкой преобразования (без него
  один неверно сопоставленный треугольник портит всё выравнивание).
- **Umeyama, S. (1991). "Least-squares estimation of transformation parameters between
  two point patterns." IEEE Trans. PAMI, 13(4), 376–380.**
  Замкнутая формула МНК-оценки преобразования подобия (поворот+масштаб+сдвиг) по
  набору соответствий точек — применяется для финальной подгонки после RANSAC
  (на всех точках-инлаерах, не на минимальной выборке).
- **Lang, D., Hogg, D. W., Mierle, K., Blanton, M., Roweis, S. (2010). "Astrometry.net:
  Blind astrometric calibration of arbitrary astronomical images." The Astronomical
  Journal, 139(5), 1782–1800.** arXiv:0910.2233. https://arxiv.org/abs/0910.2233
  «Слепое» определение точной небесной привязки кадра по звёздному каталогу — в
  проект не включаем (требует каталогов и сети), но статья использована как
  ориентир по геометрии quad-инвариантов; в будущем может пригодиться, если понадобится
  привязка кадра к реальным небесным координатам (например, для подписи объектов).
- **Evangelidis, G. D., Psarakis, E. Z. (2008). "Parametric Image Alignment Using
  Enhanced Correlation Coefficient Maximization." IEEE Trans. PAMI, 30(10), 1858–1865.**
  DOI: 10.1109/TPAMI.2008.113. Алгоритм ECC — прямое (без выделения точек) уточнение
  геометрического преобразования по яркости пикселей. В проекте зарезервирован как
  `FALLBACK`-метод регистрации переднего плана/ландшафта (когда звёзд в кадре мало или
  нужно выровнять не небо, а землю) — см. `ARCHITECTURE.md`, раздел «версия 1.1».

## 3. Стекинг (комбинирование кадров)

- **Fruchter, A. S., Hook, R. N. (2002). "Drizzle: A Method for the Linear
  Reconstruction of Undersampled Images." Publications of the Astronomical Society
  of the Pacific, 114, 144–152.** DOI: 10.1086/338393
  https://www.stsci.edu/~fruchter/dither/dither.html
  Метод объединения нескольких смещённых (dithered) кадров с сохранением фотометрии:
  каждый входной пиксель перед проецированием на выходную сетку «уменьшается» на
  коэффициент `pixfrac`, а его поток распределяется по перекрывающимся выходным
  пикселям пропорционально площади перекрытия — это позволяет частично восстановить
  разрешение выше исходного при достаточном количестве кадров со случайным
  субпиксельным смещением. Реализован как необязательный режим `DrizzleCompositor.kt`
  (v1.1) поверх базового билинейного стекинга.
- **Практика (DeepSkyStacker):** доступные методы комбинирования — среднее, медиана,
  κ-σ отбраковка (итеративное исключение пикселей, отличающихся от среднего/медианы
  больше чем на `κ·σ`), взвешенное среднее по адаптивному весу, «entropy weighted
  average», drizzle. Источник: http://deepskystacker.free.fr/english/technical.htm.
  Наш `StackCombiner.kt` по умолчанию использует κ-σ отбраковку (κ≈2.5–3, 1–2 итерации)
  с последующим средним — то же семейство методов, что и «Kappa-Sigma Clipping» в DSS;
  именно это убирает следы спутников/самолётов и одиночные «горячие» пиксели, не
  ушедшие после калибровки тёмным кадром.
- **Практика (Starry Landscape Stacker):** усечённое среднее — «отбросить выбросы,
  затем взять среднее 50% оставшихся значений, центрированных на 40-м перцентиле».
  https://sites.google.com/site/starrylandscapestacker/processing-images-with-starry-landscape-stacker-version-1-9
  Альтернативный робастный комбинатор, добавлен в `StackCombiner.kt` как режим
  `TRIMMED_MEAN` — полезен, когда в серии единичные кадры сильно отличаются
  (например, случайная засветка фарами на пейзажном первом плане).
- **Теория шума при усреднении N кадров:** случайные компоненты шума (шум чтения,
  дробовой шум) складываются в квадратуре, поэтому отношение сигнал/шум растёт как
  `√N`, а систематика (паттерн-шум, засветка) — нет, что и обосновывает саму идею
  стекинга. Общее изложение: https://siril.org/tutorials/signal-to-noise/,
  https://petapixel.com/2020/10/28/eli5-this-is-how-image-stacking-reduces-noise-and-recovers-signal/,
  https://jonrista.com/the-astrophotographers-guide/astrophotography-basics/snr/.
  Используется, чтобы оценивать в UI ожидаемый прирост SNR («стекинг N=16 кадров даёт
  ~4× по SNR») и объяснять пользователю, зачем нужно больше кадров.
- **Калибровочные кадры (тёмный кадр/dark frame):** DeepSkyStacker строит карту «горячих»
  пикселей по тёмным кадрам (снятым с закрытым объективом при тех же выдержке/ISO) и
  интерполирует их по соседям на каждом световом кадре перед регистрацией. Реализовано
  как необязательный `DarkFrameCalibrator.kt` — тёмные кадры не обязательны, но если
  пользователь их даст, качество на длинных выдержках заметно повысится.

## 4. Постобработка: удаление градиента фона

Городская засветка и виньетирование объектива создают на кадре плавный (низкочастотный)
градиент, который «съедает» слабые детали и мешает растяжке. Стандартный подход
(PixInsight `DynamicBackgroundExtraction`/`AutomaticBackgroundExtraction`, аналогично
в Siril и GraXpert): расставить сетку пробных точек, в каждой — робастная (по
σ-клиппингу) оценка фона, точки, попавшие на звёзды/туманность, отбрасываются,
через оставшиеся точки проводится гладкая поверхность (полином низкого порядка или
сплайн), которая затем вычитается из изображения. Источники (общее описание метода,
формул конкретной реализации PixInsight не публикует):
https://jonrista.com/the-astrophotographers-guide/pixinsights/dynamicbackgroundextraction/,
https://stirlingastrophoto.com/posts/multiscale-gradient-correction/,
https://astrophotons.com/pixinsight-remove-gradients-background-extraction.
Наш `BackgroundExtractor.kt` реализует ту же идею в упрощённом виде: сетка ячеек →
σ-клиппинг → полином 2-й степени по МНК → вычитание, с игнорированием ячеек, где
детектор звёзд (раздел 1) нашёл источник.

## 5. Постобработка: нелинейная растяжка (stretch)

- **Midtones Transfer Function (MTF).** Точная формула (PixInsight PCL,
  `pcl::HistogramTransformation`,
  https://pixinsight.com/developer/pcl/doc/html/classpcl_1_1HistogramTransformation.html):

  ```
  MTF(m, x) = (m − 1)·x / ((2m − 1)·x − m)
  ```

  с граничными условиями `MTF(m,0)=0`, `MTF(m,m)=0.5`, `MTF(m,1)=1`, монотонно
  возрастает и отображает [0,1] в [0,1]. Параметр `m` — «средний тон»: при `m<0.5`
  средние тона высветляются (нужно для линейного, почти чёрного стека после стекинга),
  при `m=0.5` — тождественное преобразование. Реализовано дословно в
  `MidtoneStretch.kt`; `m` подбирается автоматически так, чтобы σ-клиппированная
  медиана фона переходила в целевой уровень (~0.10–0.25), как это делает
  автоматический STF/AutoHistogram в PixInsight/Siril — плюс ручные ползунки.

## 6. Постобработка: шумоподавление и цветокалибровка

- Практика раздельного шумоподавления яркостного и цветового каналов (цветовой шум
  подавляется агрессивнее, т.к. глаз менее чувствителен к цветовому шуму, чем к
  потере детализации по яркости) — общее изложение:
  https://jonrista.com/the-astrophotographers-guide/pixinsights/effective-noise-reduction-part-1/.
  Реализовано как лёгкий медианный/билатеральный фильтр на хрома-каналах в
  `NoiseReducer.kt`; после стекинга N≥15 кадров агрессивный NR обычно и не нужен —
  основной выигрыш по шуму уже даёт сам стекинг (раздел 3).
- Полная фотометрическая цветокалибровка (PCC в PixInsight) сверяет цвет звёзд с
  каталогом (Gaia/Tycho) — для мобильного приложения избыточна. В v1 реализована
  упрощённая нейтрализация фона: цветовые каналы масштабируются так, чтобы
  σ-клиппированная медиана фона стала нейтрально-серой (`BackgroundNeutralizer.kt`) —
  убирает цветной паразитный оттенок от натриевых/светодиодных фонарей.

  (https://www.samsung.com/ie/support/mobile-devices/professional-photography-with-galaxy-expert-raw-app/).
  Режим «Astrophoto» умеет сам снимать сериями с ассистентом по созвездиям; точные
  параметры (число суб-кадров, доступность отдельных суб-экспозиций как отдельных
  файлов) официальная страница не раскрывает — это нужно проверить эмпирически на
  первой партии из 15–20 присланных снимков (см. `TESTING_PLAN.md`, шаг 0).
  **Linear DNG** отличается от «обычного» DNG тем, что демозаика уже выполнена
  (данные не байеровские RGGB, а готовый RGB) — это на самом деле ХОРОШО для нас:
  не нужен собственный демозаик/LibRaw, можно читать как обычное полноцветное
  изображение с TIFF/DNG-контейнером.
- **LibRaw** (https://www.libraw.org/) — библиотека для декодирования «настоящих»
  байеровских RAW/DNG (если пользователь всё же принесёт non-linear DNG с других
  камер). Тройное лицензирование: **LGPL2** (обязывает либо динамическую линковку,
  либо раскрытие изменений), **CDDL-1.0** (разрешает статическую линковку и закрытый
  код), «фирменная» лицензия LibRaw — выводится из употребления с версии 0.18+.
  Источник: https://www.libraw.org/node/2228,
  https://github.com/LibRaw/LibRaw/blob/master/LICENSE.CDDL. Для закрытого мобильного
  приложения при статической линковке правильный выбор — **CDDL**. В v1 LibRaw НЕ
  подключаем (см. `ARCHITECTURE.md`, ограничения) — обычный/Linear DNG и JPEG/HEIF
  покрывают ожидаемый сценарий использования.

## 8. Программы-аналоги (для сверки поведения при тестировании)

| Инструмент | Регистрация | Комбинирование | Особенность |
|---|---|---|---|
| DeepSkyStacker | треугольники звёзд, гауссов центроид | κ-σ, медиана, drizzle | тёмные/плоские/bias кадры, карта горячих пикселей |
| Starry Landscape Stacker | привязка к среднему по времени кадру | усечённое среднее (40-й перцентиль ±25%) | раздельная маска неба/земли |
| Astroalign (Python) | инварианты треугольников + k-d дерево | — (только регистрация) | открытый эталон алгоритма сопоставления |
| Sequator | звёздный трекинг + «sky vs ground» | среднее/накопление | популярен для пейзажной астрофото |
| Siril / PixInsight | звёзды или ECC | множество методов | эталон постобработки (DBE, MTF/STF, PCC) |
