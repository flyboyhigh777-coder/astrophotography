# Архитектура AstroStacker

## 0. Что это и для какого сценария

Android-приложение для склейки (стекинга) серии кадров ночного неба, снятых со
штатива (телефон не двигается между кадрами), с автоматическим выравниванием по
звёздам (компенсация видимого вращения неба) и постобработкой уровня «любительская
астрофотография»: удаление градиента засветки, растяжка, лёгкое шумоподавление,
нейтрализация цвета фона. Это НЕ замена внутреннему режиму Astrophoto в Samsung
Expert RAW (он уже сам стекает серию и отдаёт один файл) — это инструмент для
кадров, снятых как независимая серия (Pro-режим, серийная съёмка, либо отдельные
суб-кадры, если Expert RAW их сохраняет — проверяется на первой партии тестовых
фото).

## 1. Причина ограничений этой сборки — читай перед остальным

В песочнице, где написан этот код, исходящий доступ к `dl.google.com` (Android SDK,
AndroixX/Compose из Google Maven) и `repo.maven.apache.org`/`services.gradle.org`
заблокирован политикой организации (сеть отдаёт 403 на CONNECT) — это подтверждено
диагностикой прокси, не догадка. Из-за этого:

- Модуль `:app` (Android/Compose) написан полностью, но **не скомпилирован** в этой
  среде — для сборки APK его нужно открыть в Android Studio (или в CI с доступом к
  Google Maven), где Gradle сам скачает Android SDK/AndroidX/Compose при первой
  синхронизации — это стандартный первый шаг для любого Android-проекта, ничего
  специфичного делать не нужно.
- Модуль `:core` — чистый Kotlin/JVM без Android-зависимостей — написан И
  скомпилирован, И прогнан через тесты прямо здесь (компилятором `kotlinc`,
  установленным из штатного репозитория Ubuntu, полностью офлайн). Результаты — в
  `docs/TEST_RESULTS.md`.
- Реального прогона на Samsung S24 Ultra по USB из этой сессии не будет: облачная
  песочница физически не видит USB-устройство, подключённое к вашему Mac. Что для
  этого нужно — раздел `TESTING_PLAN.md`, шаг «когда телефон будет под рукой».

## 2. Модули

Для ориентира - структура всего репозитория, не только `:core`/`:app`:

```
AstroStacker/
  docs/             — этот файл, LITERATURE.md, TEST_RESULTS.md, TESTING_PLAN.md
  android-project/  — сам Android-проект (Gradle), см. дерево ниже
  validation/       — RealPhotoValidation.kt: прогон :core на настоящих фото
                      без Android/телефона, см. docs/TESTING_PLAN.md "Трек A"
  build/            — собранные и протестированные здесь core-main.jar/core-tests.jar
```

А внутри `android-project/`:

```
android-project/
  core/    — чистый Kotlin/JVM, без зависимости от Android SDK. Вся математика:
             детекция звёзд, регистрация, стекинг, постобработка.
             Из-за отсутствия Android SDK этот модуль намеренно не использует
             android.graphics.Bitmap и т.п. — только примитивные массивы,
             чтобы (а) его можно было скомпилировать и проверить прямо сейчас
             компилятором kotlinc из apt, и (б) чтобы его можно было писать
             юнит-тестами на JVM без эмулятора.
  app/     — Android-приложение (Kotlin + Jetpack Compose). Декодирование файлов,
             экран выбора кадров, прогресс, предпросмотр, экспорт. Использует :core
             как обычный Gradle-модуль (project(":core")).
```

### 2.1 `:core` — пакет `com.astrostacker.core`

- `Image.kt` — `FloatImage` (ширина/высота + 3 `FloatArray` R,G,B, значения 0..1,
  линейная светимость после декодирования гаммы) и `GrayImage` (для промежуточных
  масок/фона).
- `ColorSpace.kt` — формулы sRGB↔линейное (IEC 61966-2-1) плюс LUT для быстрого
  8-битного декодирования. Вынесена в `:core` (а не осталась Android-деталью в
  `:app`), потому что это чистая математика без зависимости от `Bitmap`, и
  потому что она напрямую влияет на корректность: `StackCombiner`/
  `MidtoneStretch` статистически корректны только для линейных данных (см.
  комментарий к `FloatImage` выше), а `:app` `ImageDecoding.kt`/
  `ProcessingViewModel.kt` обязаны прогонять пиксели через неё на входе/выходе
  пайплайна. Единственная функция во всём проекте, где граница между «нужно
  Android API» и «чистая логика» изначально казалась Android-специфичной, но
  на деле ею не является — поэтому она единственная в этом списке одновременно
  и написана для UI-слоя, и полноценно протестирована (`ColorSpaceTest`, см.
  `TEST_RESULTS.md`).
- `StarDetector.kt` — оценка локального фона по сетке ячеек с σ-клиппингом →
  порог `фон+k·σ` → связные компоненты (двухпроходная маркировка) → фильтр по
  площади/эксцентриситету → интенсивностно-взвешенный центроид с субпиксельной
  точностью. См. `LITERATURE.md` §1.
- `EarthRotationModel.kt` — по двум `EXIF DateTimeOriginal` считает ожидаемый модуль
  поворота неба `ω·Δt`, `ω=15.041″/с` (вывод — `LITERATURE.md` §2.1). Используется
  как диагностика в UI и как апостериорная проверка результата `FrameRegistrator`
  (не как вход в сам алгоритм подгонки — обоснование в `LITERATURE.md` §2.2).
- `TriangleMatcher.kt` — для каждой звезды и её k ближайших соседей строит
  треугольники, считает инвариантные (к повороту/сдвигу/масштабу) отношения сторон,
  ищет соответствия между кадрами по этим инвариантам (Groth 1986 / Astroalign 2020).
- `RansacTransformFitter.kt` + `SimilarityFit.kt` — из «шумного» набора кандидатов
  в соответствия звёзд робастно (RANSAC, Fischler & Bolles 1981) находит
  преобразование подобия (поворот θ, масштаб s≈1, сдвиг tx,ty), затем уточняет его
  МНК по всем инлаерам (замкнутая линейная форма, эквивалентная Umeyama 1991 для
  случая «подобие»). `AffineFit.kt` — запасной вариант с 6 DOF поверх того же
  набора инлаеров, см. §3.
- `FrameRegistrator.kt` — оркестрирует три шага выше для одного кадра относительно
  опорного; отбраковывает кадр целиком, если инлаеров меньше 6 или найденный угол
  сильно противоречит `EarthRotationModel` (признак облака/самолёта/сбоя).
- `StackCombiner.kt` — обратное отображение выходного пикселя в каждый кадр
  (билинейная интерполяция) → κ-σ отбраковка выбросов по стеку значений → среднее
  (по умолчанию) либо усечённое среднее либо медиана (см. `LITERATURE.md` §3).
- `TiledStacker.kt` — то же самое, но по горизонтальным полосам (tiles) выходного
  изображения, чтобы не держать все N кадров в памяти телефона одновременно
  (см. §4 ниже, память — главное ограничение на телефоне).
- `BackgroundExtractor.kt` — сетка пробных точек, σ-клиппированный робастный фон,
  игнор точек на звёздах, полином 2-й степени по МНК, вычитание.
- `MidtoneStretch.kt` — точная формула `MTF(m,x)=(m−1)x/((2m−1)x−m)` (PixInsight
  PCL), автоподбор `m` по медиане фона + ручные ползунки чёрной/белой точки.
- `BackgroundNeutralizer.kt` — нормировка каналов по σ-клиппированной медиане фона.
- `NoiseReducer.kt` — лёгкий медианный фильтр на хрома-каналах (YCbCr), яркостный
  канал не трогается или трогается минимально, чтобы не «замылить» звёзды.
- `DarkFrameCalibrator.kt` — опционально: медиана тёмных кадров → карта горячих
  пикселей → интерполяция по соседям на каждом световом кадре до регистрации.
- `Pipeline.kt` — верхнеуровневый оркестратор всех шагов с колбэком прогресса
  (`(StageProgress) -> Unit`, без корутин — модуль их не тянет как зависимость,
  чтобы оставаться «голым» JVM/Kotlin; `:app` оборачивает вызов в
  `Dispatchers.Default`).

### 2.2 `:app` — пакет `com.astrostacker.app`

- Экраны (Jetpack Compose): `FramePicker` (мульти-выбор из системного Photo
  Picker, короткая инструкция для первого раза прямо на экране, отдельный
  опциональный выбор тёмных кадров) → `Processing` (прогресс по стадиям
  пайплайна, `Stage`/`ProgressUpdate` из `:core`) → `Result` (превью, ползунок
  целевого уровня растяжки + переключатель шумоподавления, кнопка «Применить»
  пересчитывает только `Pipeline.postProcess` (фон/нейтрализация/растяжка/
  шумоподавление) над уже посчитанным линейным стеком — не весь пайплайн
  заново — и кнопка сохранения). Живой пересчёт "на лету" при каждом движении
  ползунка в v1 сознательно не делается (требует debounce и больше
  непроверенного здесь UI-кода) — только по кнопке. Навигация между тремя
  экранами — простой `when` по значению `ScreenState` (sealed interface) в
  `ProcessingViewModel`, БЕЗ Navigation-Compose: три линейных экрана без
  глубоких стеков возврата, deep links или множественных backstack'ов не
  оправдывают отдельную библиотеку и её граф-конфигурацию — обычный `when`
  проще, и его легче целиком проверить чтением (компилятора для `:app` здесь
  всё равно нет, см. §1).
- Оркестрация: `ProcessingViewModel` вызывает `:core` `Pipeline.run` в
  `viewModelScope` на `Dispatchers.Default`, публикует прогресс через
  `StateFlow`. `WorkManager`/`CoroutineWorker` для устойчивости к сворачиванию
  приложения при очень долгом стекинге — намеренно отложен на v1.1 (см. §7):
  для ожидаемых объёмов (15-20 кадров на ограниченном в п.4 разрешении)
  обычных `ViewModel`-корутин достаточно, а лишний слой, который здесь негде
  скомпилировать и проверить, — ненужный риск без обратной связи от реальной
  сборки.
- `ImageDecoding.kt` — JPEG/PNG/HEIF через `BitmapFactory` (HEIF штатно
  поддерживается с Android 9/API 28); DNG — попытка прочитать встроенный
  полноразмерный превью через `BitmapFactory` (для Linear DNG, как у Samsung
  Expert RAW, это фактически и есть полноценное RGB-изображение, см.
  `LITERATURE.md` §7); настоящий байеровский demosaic (LibRaw/NDK) — вне v1,
  зарезервирован интерфейс `RawDecoder` для последующего подключения. Каждый
  канал каждого пикселя декодированного `Bitmap` (0..255, sRGB) переводится в
  линейное 0..1 через `ColorSpace.srgbByteToLinear` из `:core` ПЕРЕД тем, как
  попасть в `FloatImage` — иначе весь дальнейший пайплайн (стекинг, растяжка)
  работал бы с гамма-кодированными значениями вопреки собственному контракту
  `FloatImage` (см. §2.1) и давал бы видимо неверный (обычно пересвеченный)
  результат.
- `MemoryBudget.kt` — расчёт безопасного суммарного числа пикселей на кадр
  (для последующего `inSampleSize`) по лимиту кучи ПРИЛОЖЕНИЯ,
  `Runtime.getRuntime().maxMemory()`. Изначально в этом документе фигурировал
  `ActivityManager.getMemoryInfo()` — от него отказались при написании кода:
  `getMemoryInfo().availMem` отражает свободную ОЗУ ВСЕЙ системы (полезно для
  вопроса «не убьёт ли систему нехватка памяти», но не отвечает на нужный
  здесь вопрос «сколько объектов может выделить КУЧА НАШЕГО процесса, прежде
  чем упасть с `OutOfMemoryError`»), а `Runtime.getRuntime().maxMemory()` —
  именно этот, прямой ответ на второй вопрос, без обращения к системным
  сервисам и `Context`. В v1 весь пайплайн, включая финальный стек, считается
  на этом ограниченном разрешении — потолок поднят до ~48 Мп (~8000×6000 px),
  выше практического разрешения телефонных камер, так что реальные фото почти
  никогда не режутся (`largeHeap` включён в манифесте) — потолок остаётся лишь
  страховкой от `OutOfMemoryError` на экстремальных сериях (много кадров и/или
  очень высокое разрешение одновременно). Региональное декодирование полного
  50-Мп кадра через `BitmapRegionDecoder` в v1 НЕ реализовано, см. честное
  обсуждение и обоснование в `ARCHITECTURE.md` §4, пункт 3.
- `ExportRepository.kt` — сохранение через `MediaStore` (Scoped Storage), формат
  PNG (без потерь, 8 бит/канал — это предел `Bitmap.compress`/`PNG` в
  публичном Android API, честно говоря: 16-бит PNG потребовал бы собственного
  кодека). Каждый канал финального `FloatImage` переводится обратно в sRGB
  через `ColorSpace.linearToSrgb` перед упаковкой в `Bitmap` — без этого шага
  сохранённая картинка выглядела бы неестественно тёмной (линейные значения,
  показанные "как есть" в sRGB-мониторе/экране телефона, систематически темнее
  того, что видит глаз).
- Локализация: `res/values/strings.xml` (русский, по умолчанию) и
  `res/values-en/strings.xml` (английский).

## 3. Почему выравнивание — «подобие», а когда — аффинное

Точный результат поворота 3D-сцены вокруг оси, проходящей через оптический центр
камеры (полюс мира, вокруг которого «вращается» звёздное небо для неподвижного
наблюдателя, — это и есть такая ось), — проективная гомография `H = K·R·K⁻¹`
(Hartley, R., Zisserman, A. «Multiple View Geometry in Computer Vision», 2nd ed.,
Cambridge University Press, 2004, гл. 8). Гомография превращается в чистый
2D-поворот только если ось вращения совпадает с оптической осью камеры; в общем
случае (полюс мира где-то сбоку или вне кадра) это не так, и точная модель имеет
8 степеней свободы.

На практике все известные инструменты (DSS, SLS, Sequator, Astroalign) всё равно
используют подобие (4 DOF: поворот θ, масштаб s≈1, сдвиг tx,ty) — потому что при
типичных интервалах между кадрами (секунды — единицы минут ⇒ угол поворота от
долей градуса до нескольких градусов) и не экстремально широком угле объектива
гомография хорошо приближается подобием, а 4 параметра надёжнее оценивать по
небольшому числу звёзд-ориентиров, чем 8. Мы делаем так же по умолчанию.

Если после RANSAC (см. `RansacTransformFitter.kt`) остаточная ошибка (RMS по
инлаерам) велика, а инлаеров достаточно (≥10), `FrameRegistrator` пересчитывает
преобразование как аффинное (6 DOF: независимые масштаб/сдвиг по осям — см.
`AffineFit.kt`, обычная линейная МНК-регрессия по уже найденным инлаерам, без
повторного RANSAC) — это покрывает, например, съёмку на ультраширокий модуль
S24 Ultra, где приближение подобием у краёв кадра слабее. Полная 8-DOF гомография
(нужен DLT/SVD) в v1 не реализована — см. дорожную карту, §7.

## 4. Память: текущее решение (v1) и честная граница того, что реализовано

50 Мп кадр в 3×float32 — это `50_000_000 × 3 × 4 байта ≈ 600 МБ` НА ОДИН кадр.
Держать в памяти 15–20 таких кадров одновременно (9–12 ГБ) на телефоне
нереалистично. Важно разделить, что из решения ниже РЕАЛИЗОВАНО в этой сборке,
а что — честная дорожная карта:

1. **Реализовано.** Все кадры декодируются через `BitmapFactory` с
   `inSampleSize`, посчитанным так, чтобы суммарное число пикселей не превышало
   безопасный предел (см. `MemoryBudget.kt` — предел зависит от
   `Runtime.getRuntime().maxMemory()`, потолок v1 — ~48 Мп, ~8000×6000 px по
   стороне). `inSampleSize` даёт только степени двойки, поэтому после него
   `ImageDecoding.decodeBitmap` доужимает результат точным билинейным ресайзом
   до фактического бюджета — иначе на промежуточных бюджетах терялось бы до
   ~75% отведённых пикселей впустую. Это даёт РАБОЧЕЕ, проверяемое v1: и
   детекция/регистрация, и сам финальный стек считаются на этом ограниченном
   разрешении — но т.к. потолок (~8000×6000 px) выше типичного разрешения
   телефонных фото, на практике v1 обычно отдаёт результат в исходном
   разрешении, а не урезанным. Для реально экстремальных серий (много кадров
   очень высокого разрешения одновременно) потолок всё ещё может сработать —
   на этом уровне работает и `TiledStacker` из `:core` (см. ниже), и он реально
   прогнан тестами (`TEST_RESULTS.md`).
2. **`TiledStacker` считает построчными полосами** — это проверенным образом
   (см. тест `tiledStacking_matchesNonTiledStacking`) не меняет результат и
   задаёт правильную СТРУКТУРУ для будущего потокового чтения, но в ТЕКУЩЕЙ
   версии он принимает уже полностью загруженные `FloatImage` и материализует
   весь выходной буфer целиком — то есть тайлинг здесь пока не снижает пиковое
   потребление памяти относительно кадров-источников, а только фиксирует
   порядок вычислений (важно для честности: не выдавать желаемое за
   действительное).
3. **Не реализовано (дорожная карта v1.1+):** полноразмерный (нативное
   разрешение сенсора) стекинг через `BitmapRegionDecoder` — когда для каждой
   полосы ВЫХОДНОГО изображения из каждого исходного файла читается только
   нужный регион (через обратное преобразование + отступ), а не файл целиком.
   Это действительно даст «по одной полосе от каждого кадра одновременно в
   памяти», но требует отдельного слоя абстракции («ленивый регионально
   читаемый источник» вместо готового `FloatImage`) поверх уже написанного и
   проверенного `TiledStacker`. Решение отложено сознательно: этот код —
   Android-специфичный, его нельзя скомпилировать и проверить в среде, где
   писалось ядро (см. §1), а ошибка в координации регионов между N файлами —
   именно то место, где легко получить трудноуловимый баг без возможности его
   прогнать. Реализовывать стоит, когда будет доступна среда со сборкой
   (Android Studio) для реальной проверки на устройстве.
4. Все промежуточные буферы в `:core` — переиспользуемые там, где это
   несложно (например, копии массивов в `StackCombiner`), чтобы не проседать
   на GC на слабом/среднем телефоне уже на нынешнем, ограниченном по
   разрешению уровне.

## 5. Лицензирование

`:core` не имеет ни одной внешней зависимости (весь код — наш), поэтому вопрос
лицензий там не встаёт. Единственная точка, где лицензия имеет значение —
опциональный будущий модуль полноценного RAW-демозаика (LibRaw, см.
`LITERATURE.md` §7): при статической линковке в закрытое приложение выбираем
CDDL-вариант LibRaw, а не LGPL2. В v1 этот модуль не подключён, поэтому вопрос
пока не актуален — фиксируем решение здесь, чтобы не забыть при добавлении.

## 7. Дорожная карта после v1

- Полноразмерный (нативное разрешение) стекинг через `BitmapRegionDecoder` —
  см. §4, пункт 3 — и, если по итогам реального использования долгий стекинг
  будет мешать (сворачивание приложения на середине), `WorkManager`/
  `CoroutineWorker` поверх уже работающей логики `ProcessingViewModel`.
- Полная проективная гомография (8 DOF, DLT + SVD) как третья ступень эскалации
  после подобия/аффинного — точная модель для поворота вокруг произвольной оси
  через центр камеры (см. §3); не реализована сейчас, чтобы не тащить в проект
  собственную SVD без внешних библиотек линейной алгебры (риск тонких численных
  ошибок без эталона для сверки).
- Drizzle-режим стекинга (`DrizzleCompositor`, Fruchter & Hook 2002) — выше
  разрешение при большом числе кадров.
- Настоящий RAW/Bayer demosaic через LibRaw/NDK (если понадобится не-Linear DNG).
- ECC-регистрация (Evangelidis & Psarakis 2008) как альтернатива для кадров почти
  без звёзд (сильная городская засветка) или для отдельного выравнивания переднего
  плана по типу Starry Landscape Stacker (маска неба/земли, раздельная склейка).
- Полноценная фотометрическая цветокалибровка по звёздному каталогу (аналог PCC).
- Калибровка по флэт-кадрам (снимок равномерно засвеченной поверхности той же
  диафрагмой) и/или фон более высокого порядка, чем полином 2-й степени
  (`BackgroundExtractor.kt`, см. `docs/LITERATURE.md` §4) - на реальных фото
  (`docs/TESTING_PLAN.md`, Трек A) низкий порядок оставляет после вычитания
  фона заметные цветные пятна по углам кадра, которые растяжка усиливает
  наравне со слабым сигналом звёзд; это не искажает регистрацию/стекинг, но
  честно ограничивает, насколько чисто разделяются реальное виньетирование
  объектива и полезный сигнал без отдельного калибровочного кадра.
